## 概述

bilirec 可以在錄製影片的同時保存直播間的彈幕、醒目留言、禮物和艦長等互動記錄。這個功能按每次錄製或每個房間單獨開啟，不會因為設定了彈幕相關環境變數就自動開始錄製。

互動記錄會保存為與影片同名的彈幕檔案。影片發生分段或斷流恢復時，彈幕檔案也會隨對應的影片分段分別保存。使用 [bilirec-web](/zh-tw/guides/web-ui/) 回放時，選擇 `jsonl` 格式可以顯示彈幕滾動和禮物等互動特效。

## 快速開始

### 在 Web 介面開啟

開始手動錄製時，在錄製選項中開啟「錄製彈幕」。

為訂閱房間開啟自動錄製時，在房間設定中開啟「錄製彈幕」。之後由該房間自動開始的錄製會沿用這個設定。

### 通過 API 開啟

手動錄製時，在開始錄製請求中加入 `record_danmaku=true`：

```bash
curl -X POST "http://127.0.0.1:8080/record/12345/start?record_danmaku=true"
```

自動錄製使用房間設定中的 `record_danmaku`：

```json
{
  "auto_record": true,
  "record_danmaku": true,
  "stream_profiles": []
}
```

### 選擇輸出格式

預設格式為 `jsonl`，適合 bilirec-web 回放。若需要與其他錄播工具交換互動記錄，可以改用 `xml`：

```bash
export DANMAKU_OUTPUT_FORMAT=jsonl
```

<Aside type="note">
Web 回放完整讀取 `jsonl`。`xml` 仍會保存彈幕與互動記錄，但 bilirec-web 不會為 XML 檔案顯示彈幕滾動和禮物特效。
</Aside>

## 設定

### `DANMAKU_OUTPUT_FORMAT`

**作用：** 選擇彈幕檔案格式。

**預設：** `jsonl`。

**可選值：** `jsonl`、`xml`。

**建議：** 大多數用戶保持 `jsonl`，這樣可以在 Web 播放器中回放彈幕和互動特效。需要兼容其他工具時再選擇 `xml`。

**影響：** 只影響新錄製的彈幕檔案格式，不影響影片格式。選擇 `xml` 後，Web 播放器仍可播放影片，但不會疊加彈幕滾動和禮物特效。

### `DANMAKU_OVERFLOW_POLICY`

**作用：** 當彈幕到達速度超過寫入速度、等待隊列已經排滿時，決定如何處理新消息。

**預設：** `drop`。

**可選值：**

- `drop`：隊列滿時丟棄新消息，優先保持錄製和彈幕連接的響應。
- `block`：等待隊列出現空位，儘量保留消息；如果磁碟寫入很慢，彈幕連接處理也可能被拖慢，彈幕處理時間可能落後於影片進度。

**建議：** 樹莓派、microSD 或同時錄製多個房間時，通常保持 `drop`。如果互動記錄完整性比連接響應更重要，並且儲存設備寫入穩定，可以考慮 `block`。

**注意：** 使用 `drop` 時，直播互動特別密集或磁碟暫時變慢，回放中可能少一些彈幕或禮物記錄。使用 `block` 時，寫入壓力高的設備可能更容易出現彈幕連接延遲或重連；在較慢的設備上，回放中的彈幕還可能晚於對應畫面，出現不同步。

### `DANMAKU_WRITER_BUFFER_SIZE`

**作用：** 彈幕寫入前用於合併數據的緩衝區大小。

**預設：** `262144` 字節（256 KB）。

**建議：** 大多數設備保持預設。提高數值可以減少小塊寫入，但會增加每個錄製任務的記憶體佔用；低記憶體設備不建議盲目增大。

### `DANMAKU_WRITER_MIN_PERIODIC_FLUSH_BYTES`

**作用：** 定期寫入時，至少積累多少彈幕數據才執行一次小週期寫入。

**預設：** `16384` 字節（16 KB）。

**建議：** 使用 microSD 或機械硬碟時保持預設，可以減少很小的寫入操作。若需要更快地把少量彈幕推進儲存設備，可以適當減小，但寫入次數會增加。

### `DANMAKU_WRITER_FLUSH_PERIOD_SECS`

**作用：** 定期把已接收的彈幕數據推進儲存設備的間隔。

**預設：** `15` 秒。

**建議：** 與影片寫入的預設週期一致，適合作為一般起點。儲存設備寫入較慢時可以適當增大，以減少寫入頻率；更重視異常中斷時少丟最近數據時可以適當減小。

**代價：** 間隔越大，記憶體中等待寫入的數據和異常中斷時尚未推進的數據窗口可能越大；間隔越小，寫入次數和設備壓力會增加。

### `DANMAKU_WRITER_SYNC_PERIOD_SECS`

**作用：** 定期強制把彈幕檔案完整落盤，而不只是寫入操作系統緩存。

**預設：** `0`（錄製過程中不定期強制落盤，結束錄製時再完成保存）。

**建議：** microSD 和低功耗設備通常保持 `0`，減少額外寫入。若設備經常突然斷電，並且更重視減少最近數據丟失，可以設定為大於 `0` 的秒數。

**代價：** 設定為大於 `0` 會更頻繁地處理整個彈幕檔案，可能增加儲存設備寫入壓力。它主要改善異常斷電時的數據安全，不會讓 Web 播放器獲得更多彈幕。

### `DANMAKU_CHAN_BUFFER_SIZE`

**作用：** 設定彈幕接收和寫入過程可以暫存的消息槽位數量。

**預設：** `256`。

**建議：** 彈幕密集、儲存設備偶爾出現短暫寫入延遲時，可以適當增大。記憶體緊張或錄製路數較多時，可以保持預設或適當減小。

**注意：** 隊列較大時可以吸收更短的消息高峰，但記憶體佔用也會增加；它不能解決持續的寫入速度不足。

### `DANMAKU_BYTES_POOL_SIZE`

**作用：** 設定彈幕片段緩衝的基礎大小，供程式重複利用記憶體。

**預設：** `4096` 字節（4 KB）。

**建議：** 保持預設。除非已經確認彈幕處理存在大量記憶體分配或設備有明確的記憶體限制，否則不建議單獨調整。

**影響：** 數值較大可能減少擴容和分配次數，但會提高記憶體池佔用；數值較小則節省部分記憶體，但密集互動時可能增加分配開銷。

## 推薦設定

### 保守

適合樹莓派、Android 或 microSD：

```bash
export DANMAKU_OUTPUT_FORMAT=jsonl
export DANMAKU_OVERFLOW_POLICY=drop
export DANMAKU_WRITER_FLUSH_PERIOD_SECS=15
export DANMAKU_WRITER_SYNC_PERIOD_SECS=0
```

優先保持錄製響應與儲存設備壽命，極端擁堵時允許少量互動記錄缺失。

### 完整記錄優先

適合寫入性能穩定、且更重視互動記錄完整性的設備：

```bash
export DANMAKU_OUTPUT_FORMAT=jsonl
export DANMAKU_OVERFLOW_POLICY=block
```

隊列滿時儘量等待寫入，但磁碟擁堵可能影響彈幕連接處理。若出現頻繁重連或整體錄製壓力升高，可以改回 `drop`。

<Aside type="caution">
在 microSD、機械硬碟或其他寫入較慢的環境中使用 `block` 時，隊列滿會讓彈幕接收處理等待寫入。影片錄製通常仍會繼續，但彈幕處理可能落後於影片進度，回放時可能出現彈幕延遲或與影片不同步；遇到這種情況，優先改回 `drop`。
</Aside>

### 外部工具

需要把記錄交給支持 XML 的外部工具時：

```bash
export DANMAKU_OUTPUT_FORMAT=xml
export DANMAKU_OVERFLOW_POLICY=drop
```

這種設定仍會保存互動記錄，但 bilirec-web 回放不會顯示彈幕滾動和禮物特效。

## 性能調節

彈幕寫入通常不是影片錄製記憶體佔用的主要來源。預設彈幕緩衝遠小於影片讀寫緩衝，規劃設備記憶體時仍應優先參考[記憶體佔用估算](/zh-tw/configuration/memory-estimation/)。

如果出現以下症狀，可以按順序處理：

- **回放中彈幕明顯變少：** 先確認 `DANMAKU_OUTPUT_FORMAT` 為 `jsonl`，再檢查是否使用了 `drop`，以及磁碟是否在同時處理多路錄製或轉碼。
- **彈幕連接頻繁重連：** 先保持 `DANMAKU_OVERFLOW_POLICY=drop`，再檢查網路和儲存設備寫入延遲。不要只通過增大隊列掩蓋持續的寫入瓶頸。
- **記憶體逐漸升高：** 優先檢查影片錄製路數和影片緩衝設定；只有確認彈幕隊列排滿時，才考慮減小 `DANMAKU_CHAN_BUFFER_SIZE` 或 `DANMAKU_WRITER_BUFFER_SIZE`。
- **microSD 寫入壓力高：** 保持 `DANMAKU_WRITER_SYNC_PERIOD_SECS=0`，並避免把 `DANMAKU_WRITER_FLUSH_PERIOD_SECS` 調得過小。

## 檔案與儲存行為

- 彈幕檔案與對應影片使用相同的基礎檔案名，只改變擴展名。
- HTTP-FLV 發生分段、HLS-fMP4 的媒體初始化信息發生變化，或斷流恢復後開始新影片檔案時，彈幕記錄也會切換到對應的新檔案。
- 停止錄製時，程式會結束當前彈幕檔案並寫入完整結尾。正常結束後檔案可以被讀取。
- `DANMAKU_WRITER_SYNC_PERIOD_SECS=0` 時，錄製過程中不會定期強制整個檔案落盤；這可以減少 microSD 寫入，但突然斷電時最近尚未落盤的數據可能無法保留。
- 彈幕寫入失敗不會主動終止影片錄製。需要完整記錄時，仍應關注日誌、磁碟空間和[監控指標](/zh-tw/configuration/metrics/)。

## 網路行為

彈幕通過 Bilibili 的實時連接接收。連接中斷後程式會自動重試；連接持續成功一段時間後，重試等待會重新從較短間隔開始。

如果獲取彈幕連接信息失敗，程式會嘗試使用備用連接地址。網路不穩定、Bilibili 臨時限制請求或儲存設備寫入變慢，都可能造成部分互動記錄缺失或延遲。

彈幕連接與影片錄製分開處理。彈幕暫時不可用時，影片錄製通常仍會繼續；恢復連接後會繼續記錄，但斷開期間無法補回已經錯過的互動。

## 故障排查

### 已開啟錄製彈幕，但沒有彈幕檔案

確認本次錄製或房間自動錄製設定確實開啟了 `record_danmaku`，並檢查錄製目錄權限和可用空間。僅設定 `DANMAKU_*` 不會自動開啟彈幕錄製。

### 有彈幕檔案，但播放器沒有彈幕滾動

確認 `DANMAKU_OUTPUT_FORMAT=jsonl`，並檢查彈幕檔案是否與 MP4 使用相同的基礎檔案名。XML 檔案可以保存互動記錄，但 bilirec-web 不會用它顯示回放疊加效果。

### 彈幕檔案比影片檔案多

這通常是正常現象。影片在 PK、流參數變化或斷流恢復後可能產生多個分段，每個影片分段都會對應自己的彈幕檔案。按相同基礎檔案名配對即可。

### 錄製中無法讀取彈幕

正在寫入的當前分段不會通過彈幕讀取接口提供。停止錄製並完成檔案後，再從檔案管理或回放頁面讀取。

### 彈幕消息丟失

如果使用 `DANMAKU_OVERFLOW_POLICY=drop`，隊列排滿時會主動丟棄新消息，這是為了避免彈幕處理拖住錄製。可以檢查磁碟寫入延遲和並發錄製數；在儲存設備性能足夠時，再考慮使用 `block`。

## 進階說明

`jsonl` 中會保存普通彈幕、醒目留言、禮物和艦長等事件，並帶有相對影片分段開始時間的時間戳，播放器據此在對應時刻顯示內容。指標頁中的彈幕指標可以幫助判斷連接、消息處理和寫入是否出現擁堵。
