如果你已經用 Grafana 接上 VictoriaMetrics（在 Grafana 裡添加資料源時選 Prometheus 這一類），可以把指標儀表盤的 JSON 導入進去，省去從零寫查詢。日誌分析儀表盤則使用 VictoriaLogs datasource plugin，兩者是不同資料源。各張盤對應不同問題，按需要下載即可。指標如何開啟、如何被抓取，見 [監控指標](/zh-tw/configuration/metrics/)。時序庫和 Grafana 的安裝見各項目官方文檔。

請下載**與當前文檔語言相同**的 JSON。簡繁兩套盤共用同一 `uid`，後導入的會覆蓋先導入的。

## 快速開始

1. 指標儀表盤需要 Grafana、VictoriaMetrics 或 Prometheus，且 bilirec 已開啟指標並被抓取（見 [監控指標](/zh-tw/configuration/metrics/)）；日誌儀表盤需要 VictoriaLogs 與 [VictoriaLogs datasource plugin](https://grafana.com/grafana/plugins/victoriametrics-logs-datasource/)，其中“日誌分析”的傳輸健康區塊也會讀取 Prometheus metrics。
2. 在 Grafana 添加資料源：指標盤選 Prometheus，地址填 VictoriaMetrics 或 Prometheus；日誌盤選 `VictoriaLogs`，地址填 VictoriaLogs。
3. Grafana → **Dashboards → Import** → 上傳本頁對應語言的 JSON（或粘貼內容）。
4. 導入後在頂欄選 **資料源**；指標盤的 `job` / `instance` 一般保持 All。“日誌分析”請同時選擇日誌資料源與指標資料源；“原始日誌瀏覽”只需選擇 VictoriaLogs 資料源。

可以從 **錄製總覽** 開始看。其餘 9 張帶相同 `bilirec` 標籤，頂欄下拉可互相跳轉，並保留時間範圍與變數。

## 該選哪一張

按你想看的問題選盤：

| 你想知道什麼 | 儀表盤 |
|--------------|--------|
| 現在有幾路在錄？誰開播卻沒在錄？今天已經寫了多少？ | [錄製總覽](#錄製總覽) |
| 開錄失敗、斷線恢復、錄著但流沒連上？ | [錄製健康](#錄製健康) |
| 彈幕是不是丟了、重連很勤、切檔卡住？ | [彈幕健康](#彈幕健康) |
| 轉碼有沒有積壓、失敗突然變多，FFmpeg 與 CloudConvert 各處理了多少？ | [轉碼健康](#轉碼健康) |
| 記憶體 / CPU 是不是被錄製抬高？高的是程式還是檔案緩存？ | [行程資源](#行程資源) |
| 這段時間一共錄了多少、誰最吃磁碟？ | [累計用量](#累計用量) |
| 每天趨勢怎樣、磁碟大概還能撐多久？ | [用量趨勢](#用量趨勢) |
| 某一個房間今晚錄沒錄上、斷過幾次？ | [單房間詳情](#單房間詳情) |
| 想看日誌量趨勢、錯誤告警與房間 / 模塊維度？ | [日誌分析](#日誌分析) |
| 想盯原始日誌、反覆調 LogsQL，或直接查看錄製 / 轉碼 / 檔案寫入內容？ | [原始日誌瀏覽](#原始日誌瀏覽) |

日常先看總覽往往就夠；排查錄製、彈幕或轉碼異常時再打開對應的健康盤，關心磁碟佔用時再看趨勢或累計。某個主播的細節用單房間。沒開彈幕錄製時，「彈幕健康」會是空的。

## 日誌分析

![日誌分析](/images/dashboards/bilirec-logging.png)

**用途：** 用 VictoriaLogs 看 bilirec 日誌趨勢與分佈，並可按房間、模塊、級別、主機過濾。

**能回答：**

- 哪些房間或模塊在這段時間產生日誌最多？
- error / warn 是否突然增加？
- 某一台主機或某個房間是否集中出現異常日誌？
- 選定時間內有多少日誌被丟棄、請求失敗或發生重試？當前發送隊列多大？
- 如何把多個房間、模塊與級別條件組合起來查？

**下載：** [bilirec-logging.json](/dashboards/zh-tw/bilirec-logging.json)

**注意：** 日誌面板需要 VictoriaLogs datasource plugin；傳輸健康四個面板還會讀取 Prometheus metrics，所以也要開啟 [監控指標](/zh-tw/configuration/metrics/) 並選對指標資料源。要看原始內容請用 [原始日誌瀏覽](#原始日誌瀏覽)。

## 原始日誌瀏覽

![原始日誌瀏覽](/images/dashboards/bilirec-logs-explorer.png)

**用途：** 專注查看原始日誌內容，並用房間、模塊、級別、主機與 LogsQL 組合過濾。

**能回答：**

- 篩選後的原始日誌內容是什麼？
- 最近的 error / warn 實際內容與結構化字段是什麼？
- 某個房間的開錄、輪轉、停止或斷線恢復過程發生了什麼？
- 轉碼任務為何延後或失敗？對應 `task_id` 是什麼？
- 哪個檔案在創建、寫入、flush、sync 或釋放頁面緩存時出現問題？

**下載：** [bilirec-logs-explorer.json](/dashboards/zh-tw/bilirec-logs-explorer.json)

**注意：** 第二列的“LogsQL 字段”和“完整 LogsQL”會應用到所有日誌面板。請用這兩個做過濾，不要用 Logs 面板內置的字段搜索。

## 錄製總覽

![錄製總覽](/images/dashboards/bilirec-overview.png)

**用途：** 適合當作第一張打開的盤。看現在在錄幾路、多少房間開播、今天已經寫了多少、近期斷線恢復，以及「開播但目前沒在錄」。

**能回答：**

- 現在有沒有在錄？
- 誰在播卻沒錄（只開了開播通知、不自動錄製的房間也會出現）？
- 今天從 0 點到現在已經寫入多少（用來判斷還要不要繼續錄）？
- 剛才是不是集中斷過流？

**下載：** [bilirec-overview.json](/dashboards/zh-tw/bilirec-overview.json)

**注意：** 預設時間範圍約 6 小時；「寫入量」按當天 0 點起算（面板上會標「今天迄今」），不受這個範圍影響。碼率見盤裡的「全站直播流讀取速率」。

## 錄製健康

![錄製健康](/images/dashboards/bilirec-recording.png)

**用途：** 排查「以為在錄、其實沒連上流」或開錄失敗。

**能回答：**

- 失敗是磁碟滿、達到同時路數、房間加密/封禁，還是流地址連不上？
- 恢復是成功多還是放棄多？
- 有沒有過短分段被丟掉？

**下載：** [bilirec-recording.json](/dashboards/zh-tw/bilirec-recording.json)

**注意：** 沒人在恢復時，「錄製中但流沒連上」為空是正常的。碼率見 [錄製總覽](#錄製總覽)。

## 彈幕健康

![彈幕健康](/images/dashboards/bilirec-danmaku.png)

**用途：** 只在開啟彈幕錄製時有意義。

**能回答：**

- 消息是不是因為寫入來不及被丟掉？
- 重連是否異常頻繁？
- 切檔通知是不是也被丟掉（彈幕會繼續寫進舊檔）？

**下載：** [bilirec-danmaku.json](/dashboards/zh-tw/bilirec-danmaku.json)

**注意：** 沒有正在錄彈幕時整張會空。丟棄只在溢出策略為丟棄、且寫入來不及（隊列已滿）時增加；可結合 [彈幕錄製](/zh-tw/configuration/danmaku/) 檢查策略、儲存與並發路數。

## 轉碼健康

**用途：** 排查轉碼積壓與失敗。版面與「錄製健康」相同：先看現狀 KPI，再看積壓 / 失敗率，最後是趨勢與 FFmpeg / CloudConvert 對比。

**能回答：**

- 現在有多少任務在處理、在本機排隊？
- 這段時間入隊、完成、失敗嘗試、取消各多少？
- 區間失敗率高不高（失敗嘗試 ÷ 完成+失敗；重試會抬高）？
- 積壓是 FFmpeg 還是 CloudConvert？落在哪臺 instance？
- 兩邊入隊與結果速率有沒有突然分開？

**下載：** [bilirec-convert.json](/dashboards/zh-tw/bilirec-convert.json)

**注意：** 「失敗」按失敗嘗試計數，重試會重複累加。CloudConvert 的「待處理」是尚未成功提交到雲端，「處理中」是已提交但仍在雲端等待、執行或下載結果。預設時間範圍約 6 小時，與其他健康盤一致。沒有轉碼任務時「各實例積壓」為空是正常的。

## 行程資源

![行程資源](/images/dashboards/bilirec-runtime.png)

**用途：** 對照「同時在錄幾路」看 CPU / 記憶體。Linux 上會把程式自己佔用的記憶體和用來加速讀檔案的緩存分開顯示，避免把緩存當成程式在漲記憶體。

**能回答：**

- 記憶體高是不是錄製檔案緩存？（見 [記憶體佔用估算](/zh-tw/configuration/memory-estimation/)）
- CPU 是否隨路數一起抬高？
- 打開的檔案數是否異常？

**下載：** [bilirec-runtime.json](/dashboards/zh-tw/bilirec-runtime.json)

**注意：** Windows 上可能只有一項總記憶體，沒有把檔案緩存拆開。

## 累計用量

![累計用量](/images/dashboards/bilirec-totals.png)

**用途：** 看選定時間範圍內的合計與 Top N 房間，不是「此刻」狀態。

**能回答：**

- 這 7 天大概寫了多少？
- 哪個房間最吃空間？
- 錄製時長和開播時長差多少？

**下載：** [bilirec-totals.json](/dashboards/zh-tw/bilirec-totals.json)

**注意：** 寫入量約等於錄製檔案寫到磁碟的量，不是整臺機器還剩多少空間。錄製 / 開播時長依賴 VictoriaMetrics；純 Prometheus 這些面板會空。預設約 7 天。

## 用量趨勢

![用量趨勢](/images/dashboards/bilirec-trends.png)

**用途：** 看走勢和磁碟還能撐多久。上方 KPI 是這段總增量再換成「平均每小時 / 天」。

**能回答：**

- 每天寫入是否在漲？
- 平均每天錄過幾個房間、開播裡有多少有在錄？
- 按當前寫入速度，磁碟大概何時用完？

**下載：** [bilirec-trends.json](/dashboards/zh-tw/bilirec-trends.json)

**注意：**

- 中間「每日」點是該時刻往回 24 小時，不是日曆日 0:00–24:00；時間範圍建議至少 7 天。
- 磁碟還能撐多久，需要主機也提供磁碟空間指標（常見做法是裝 node_exporter，ZFS 盤優先用它的數據）。沒有這些指標時，錄製相關圖仍有數，磁碟預估為空。
- 磁碟預估虛線同樣依賴 VictoriaMetrics。

## 單房間詳情

![單房間詳情](/images/dashboards/bilirec-room.png)

**用途：** 頂欄選一個房間（下拉顯示主播名，實際值仍是房間號），看開播 / 錄製 / 連線 / 彈幕時間線。

**能回答：**

- 這場直播有沒有完整錄上？
- 中途流斷過幾次？
- 這段時間寫了多少、彈幕多少條？

**下載：** [bilirec-room.json](/dashboards/zh-tw/bilirec-room.json)

**注意：** 頂欄先選一個房間；未選時面板是空的。

## 導入後常見現象

- 這些 JSON 的資料源類型是 Prometheus，地址指向 VictoriaMetrics。部分時長和磁碟預估用了 VictoriaMetrics 的查詢函數，純 Prometheus 裡對應面板會空。
- **日誌分析盤沒有日誌數據：** 請確認已安裝 VictoriaLogs datasource plugin、資料源地址可連通，並在頂欄選擇日誌資料源。
- **日誌分析盤的傳輸健康區塊沒有數據：** 請確認已開啟 bilirec metrics、Prometheus/VictoriaMetrics 已抓取，並在頂欄選擇指標資料源。
- **`job` / `instance` 對不上**時整張沒數：抓取設定裡的標籤要能在下拉里出現。
- **圖例沒有主播名：** 房間下拉已用 `bilirec_room_info` 拼上主播名；若仍只有房間號，見 [監控指標](/zh-tw/configuration/metrics/) 中「顯示主播名」的說明。
- **自己畫「平均同時錄製」偏大：** 見 [常見問題 · 平均同時錄製](/zh-tw/guides/faq/#grafana-裡平均同時錄製比實際同時路數大很多) 與指標頁「先加總再對時間平均」。用量趨勢盤的「錄製房間數」是每天錄過幾間（不論錄多久），不是同時路數。
- **空表不一定壞了：** 沒人在恢復、沒開彈幕、沒有主機磁碟指標時，對應區塊本來就是空的。

指標清單與查詢寫法見 [監控指標](/zh-tw/configuration/metrics/)。
