## 概述

bilirec 可以在录制视频的同时保存直播间的弹幕、醒目留言、礼物和舰长等互动记录。这个功能按每次录制或每个房间单独开启，不会因为设置了弹幕相关环境变量就自动开始录制。

互动记录会保存为与视频同名的弹幕文件。视频发生分段或断流恢复时，弹幕文件也会随对应的视频分段分别保存。使用 [bilirec-web](/zh-cn/guides/web-ui/) 回放时，选择 `jsonl` 格式可以显示弹幕滚动和礼物等互动特效。

## 快速开始

### 在 Web 界面开启

开始手动录制时，在录制选项中开启「录制弹幕」。

为订阅房间开启自动录制时，在房间配置中开启「录制弹幕」。之后由该房间自动开始的录制会沿用这个设置。

### 通过 API 开启

手动录制时，在开始录制请求中加入 `record_danmaku=true`：

```bash
curl -X POST "http://127.0.0.1:8080/record/12345/start?record_danmaku=true"
```

自动录制使用房间配置中的 `record_danmaku`：

```json
{
  "auto_record": true,
  "record_danmaku": true,
  "stream_profiles": []
}
```

### 选择输出格式

默认格式为 `jsonl`，适合 bilirec-web 回放。若需要与其他录播工具交换互动记录，可以改用 `xml`：

```bash
export DANMAKU_OUTPUT_FORMAT=jsonl
```

<Aside type="note">
Web 回放完整读取 `jsonl`。`xml` 仍会保存弹幕与互动记录，但 bilirec-web 不会为 XML 文件显示弹幕滚动和礼物特效。
</Aside>

## 配置

### `DANMAKU_OUTPUT_FORMAT`

**作用：** 选择弹幕文件格式。

**默认：** `jsonl`。

**可选值：** `jsonl`、`xml`。

**建议：** 大多数用户保持 `jsonl`，这样可以在 Web 播放器中回放弹幕和互动特效。需要兼容其他工具时再选择 `xml`。

**影响：** 只影响新录制的弹幕文件格式，不影响视频格式。选择 `xml` 后，Web 播放器仍可播放视频，但不会叠加弹幕滚动和礼物特效。

### `DANMAKU_OVERFLOW_POLICY`

**作用：** 当弹幕到达速度超过写入速度、等待队列已经排满时，决定如何处理新消息。

**默认：** `drop`。

**可选值：**

- `drop`：队列满时丢弃新消息，优先保持录制和弹幕连接的响应。
- `block`：等待队列出现空位，尽量保留消息；如果磁盘写入很慢，弹幕连接处理也可能被拖慢，弹幕处理时间可能落后于视频进度。

**建议：** 树莓派、microSD 或同时录制多个房间时，通常保持 `drop`。如果互动记录完整性比连接响应更重要，并且储存设备写入稳定，可以考虑 `block`。

**注意：** 使用 `drop` 时，直播互动特别密集或磁盘暂时变慢，回放中可能少一些弹幕或礼物记录。使用 `block` 时，写入压力高的设备可能更容易出现弹幕连接延迟或重连；在较慢的设备上，回放中的弹幕还可能晚于对应画面，出现不同步。

### `DANMAKU_WRITER_BUFFER_SIZE`

**作用：** 弹幕写入前用于合并数据的缓冲区大小。

**默认：** `262144` 字节（256 KB）。

**建议：** 大多数设备保持默认。提高数值可以减少小块写入，但会增加每个录制任务的内存占用；低内存设备不建议盲目增大。

### `DANMAKU_WRITER_MIN_PERIODIC_FLUSH_BYTES`

**作用：** 定期写入时，至少积累多少弹幕数据才执行一次小周期写入。

**默认：** `16384` 字节（16 KB）。

**建议：** 使用 microSD 或机械硬盘时保持默认，可以减少很小的写入操作。若需要更快地把少量弹幕推进储存设备，可以适当减小，但写入次数会增加。

### `DANMAKU_WRITER_FLUSH_PERIOD_SECS`

**作用：** 定期把已接收的弹幕数据推进储存设备的间隔。

**默认：** `15` 秒。

**建议：** 与视频写入的默认周期一致，适合作为一般起点。储存设备写入较慢时可以适当增大，以减少写入频率；更重视异常中断时少丢最近数据时可以适当减小。

**代价：** 间隔越大，内存中等待写入的数据和异常中断时尚未推进的数据窗口可能越大；间隔越小，写入次数和设备压力会增加。

### `DANMAKU_WRITER_SYNC_PERIOD_SECS`

**作用：** 定期强制把弹幕文件完整落盘，而不只是写入操作系统缓存。

**默认：** `0`（录制过程中不定期强制落盘，结束录制时再完成保存）。

**建议：** microSD 和低功耗设备通常保持 `0`，减少额外写入。若设备经常突然断电，并且更重视减少最近数据丢失，可以设置为大于 `0` 的秒数。

**代价：** 设置为大于 `0` 会更频繁地处理整个弹幕文件，可能增加储存设备写入压力。它主要改善异常断电时的数据安全，不会让 Web 播放器获得更多弹幕。

### `DANMAKU_CHAN_BUFFER_SIZE`

**作用：** 设置弹幕接收和写入过程可以暂存的消息槽位数量。

**默认：** `256`。

**建议：** 弹幕密集、储存设备偶尔出现短暂写入延迟时，可以适当增大。内存紧张或录制路数较多时，可以保持默认或适当减小。

**注意：** 队列较大时可以吸收更短的消息高峰，但内存占用也会增加；它不能解决持续的写入速度不足。

### `DANMAKU_BYTES_POOL_SIZE`

**作用：** 设置弹幕片段缓冲的基础大小，供程序重复利用内存。

**默认：** `4096` 字节（4 KB）。

**建议：** 保持默认。除非已经确认弹幕处理存在大量内存分配或设备有明确的内存限制，否则不建议单独调整。

**影响：** 数值较大可能减少扩容和分配次数，但会提高内存池占用；数值较小则节省部分内存，但密集互动时可能增加分配开销。

## 推荐设置

### 保守

适合树莓派、Android 或 microSD：

```bash
export DANMAKU_OUTPUT_FORMAT=jsonl
export DANMAKU_OVERFLOW_POLICY=drop
export DANMAKU_WRITER_FLUSH_PERIOD_SECS=15
export DANMAKU_WRITER_SYNC_PERIOD_SECS=0
```

优先保持录制响应与储存设备寿命，极端拥堵时允许少量互动记录缺失。

### 完整记录优先

适合写入性能稳定、且更重视互动记录完整性的设备：

```bash
export DANMAKU_OUTPUT_FORMAT=jsonl
export DANMAKU_OVERFLOW_POLICY=block
```

队列满时尽量等待写入，但磁盘拥堵可能影响弹幕连接处理。若出现频繁重连或整体录制压力升高，可以改回 `drop`。

<Aside type="caution">
在 microSD、机械硬盘或其他写入较慢的环境中使用 `block` 时，队列满会让弹幕接收处理等待写入。视频录制通常仍会继续，但弹幕处理可能落后于视频进度，回放时可能出现弹幕延迟或与视频不同步；遇到这种情况，优先改回 `drop`。
</Aside>

### 外部工具

需要把记录交给支持 XML 的外部工具时：

```bash
export DANMAKU_OUTPUT_FORMAT=xml
export DANMAKU_OVERFLOW_POLICY=drop
```

这种设置仍会保存互动记录，但 bilirec-web 回放不会显示弹幕滚动和礼物特效。

## 性能调节

弹幕写入通常不是视频录制内存占用的主要来源。默认弹幕缓冲远小于视频读写缓冲，规划设备内存时仍应优先参考[内存占用估算](/zh-cn/configuration/memory-estimation/)。

如果出现以下症状，可以按顺序处理：

- **回放中弹幕明显变少：** 先确认 `DANMAKU_OUTPUT_FORMAT` 为 `jsonl`，再检查是否使用了 `drop`，以及磁盘是否在同时处理多路录制或转码。
- **弹幕连接频繁重连：** 先保持 `DANMAKU_OVERFLOW_POLICY=drop`，再检查网络和储存设备写入延迟。不要只通过增大队列掩盖持续的写入瓶颈。
- **内存逐渐升高：** 优先检查视频录制路数和视频缓冲配置；只有确认弹幕队列排满时，才考虑减小 `DANMAKU_CHAN_BUFFER_SIZE` 或 `DANMAKU_WRITER_BUFFER_SIZE`。
- **microSD 写入压力高：** 保持 `DANMAKU_WRITER_SYNC_PERIOD_SECS=0`，并避免把 `DANMAKU_WRITER_FLUSH_PERIOD_SECS` 调得过小。

## 文件与储存行为

- 弹幕文件与对应视频使用相同的基础文件名，只改变扩展名。
- HTTP-FLV 发生分段、HLS-fMP4 的媒体初始化信息发生变化，或断流恢复后开始新视频文件时，弹幕记录也会切换到对应的新文件。
- 停止录制时，程序会结束当前弹幕文件并写入完整结尾。正常结束后文件可以被读取。
- `DANMAKU_WRITER_SYNC_PERIOD_SECS=0` 时，录制过程中不会定期强制整个文件落盘；这可以减少 microSD 写入，但突然断电时最近尚未落盘的数据可能无法保留。
- 弹幕写入失败不会主动终止视频录制。需要完整记录时，仍应关注日志、磁盘空间和[监控指标](/zh-cn/configuration/metrics/)。

## 网络行为

弹幕通过 Bilibili 的实时连接接收。连接中断后程序会自动重试；连接持续成功一段时间后，重试等待会重新从较短间隔开始。

如果获取弹幕连接信息失败，程序会尝试使用备用连接地址。网络不稳定、Bilibili 临时限制请求或储存设备写入变慢，都可能造成部分互动记录缺失或延迟。

弹幕连接与视频录制分开处理。弹幕暂时不可用时，视频录制通常仍会继续；恢复连接后会继续记录，但断开期间无法补回已经错过的互动。

## 故障排查

### 已开启录制弹幕，但没有弹幕文件

确认本次录制或房间自动录制配置确实开启了 `record_danmaku`，并检查录制目录权限和可用空间。仅设置 `DANMAKU_*` 不会自动开启弹幕录制。

### 有弹幕文件，但播放器没有弹幕滚动

确认 `DANMAKU_OUTPUT_FORMAT=jsonl`，并检查弹幕文件是否与 MP4 使用相同的基础文件名。XML 文件可以保存互动记录，但 bilirec-web 不会用它显示回放叠加效果。

### 弹幕文件比视频文件多

这通常是正常现象。视频在 PK、流参数变化或断流恢复后可能产生多个分段，每个视频分段都会对应自己的弹幕文件。按相同基础文件名配对即可。

### 录制中无法读取弹幕

正在写入的当前分段不会通过弹幕读取接口提供。停止录制并完成文件后，再从文件管理或回放页面读取。

### 弹幕消息丢失

如果使用 `DANMAKU_OVERFLOW_POLICY=drop`，队列排满时会主动丢弃新消息，这是为了避免弹幕处理拖住录制。可以检查磁盘写入延迟和并发录制数；在储存设备性能足够时，再考虑使用 `block`。

## 进阶说明

`jsonl` 中会保存普通弹幕、醒目留言、礼物和舰长等事件，并带有相对视频分段开始时间的时间戳，播放器据此在对应时刻显示内容。指标页中的弹幕指标可以帮助判断连接、消息处理和写入是否出现拥堵。
