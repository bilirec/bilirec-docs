bilirec 可以在**独立端口**暴露 Prometheus 格式的指标，供 VictoriaMetrics（或任何兼容 Prometheus 抓取协议的采集器）抓取。之后可以在 Grafana 里画图、做每日合计。**默认关闭**，开启不影响主 API 端口、路由与认证。

适用场景：在 NAS / 树莓派上长时间录制时，想看资源占用、每房间写入量、录制时长和开播情况。

bilirec 只负责把当前指标公开出来，不会自己保存历史，也不会画图。要把数字留下来，需要另外安装 [VictoriaMetrics](https://docs.victoriametrics.com/quick-start/) 或 [Prometheus](https://prometheus.io/docs/prometheus/latest/getting_started/)，让它们定期来抓 `/metrics`。要用图形界面时，再装 [Grafana](https://grafana.com/docs/grafana/latest/setup-grafana/installation/)；也可以先用 VictoriaMetrics / Prometheus 自带的查询页。安装步骤以各项目文档为准，本页说明如何让它们抓到 bilirec。

已经接好 Grafana 时，也可以导入一组现成面板，见 [Grafana 仪表盘](/zh-cn/configuration/grafana-dashboards/)。自己按下文查询做图同样可行。

## 前置知识

监控指标涉及 Prometheus 抓取协议、时序数据库与可视化面板，需要一定的运维基础。如果你不熟悉相关概念，可先阅读以下官方文档：

- [Prometheus 入门](https://prometheus.io/docs/prometheus/latest/getting_started/) — 抓取协议、`/metrics` 端点与 PromQL 基础
- [VictoriaMetrics 文档](https://docs.victoriametrics.com/) — bilirec 推荐的时序数据库；查询用 [MetricsQL 函数参考](https://docs.victoriametrics.com/metricsql/)（与 PromQL 兼容，含 `increase`、`rate`、`integrate` 等）
- [Grafana 入门](https://grafana.com/docs/grafana/latest/fundamentals/getting-started/) — 数据源配置、面板与仪表盘搭建

bilirec 只负责暴露指标，采集与可视化由上述工具完成。下面假设时序数据库已经装好，并且你大致了解这些工具的基本用法。

## 快速开始

1. 安装 VictoriaMetrics 或 Prometheus；要用图形界面时再装 Grafana（见上文链接）
2. 在 `.env` 中设置 `METRICS_ENABLED=true`，按需调整 `METRICS_PORT`
3. 重启 bilirec，日志会打印 `metrics 服务器已启动：http://<addr>:9090/metrics`
4. 在 VictoriaMetrics（或 vmagent / Prometheus）的抓取配置中加入 bilirec 地址，`scrape_interval` 建议 `15–30s`
5. 在 Grafana 添加 Prometheus 类型数据源后，可用下文查询做图，也可以导入 [Grafana 仪表盘](/zh-cn/configuration/grafana-dashboards/)

```bash
export METRICS_ENABLED=true
export METRICS_HOST=          # 留空监听所有网卡，便于跨机器抓取
export METRICS_PORT=9090
```

<Aside type="caution">
指标端口**没有认证**，任何能访问该端口的人都能读取指标。若端口可能被公网访问，建议通过防火墙或反向代理限制来源；不建议直接将 `METRICS_PORT` 暴露到公网。
</Aside>

## 配置

| 变量 | 说明 | 默认值 |
|------|------|--------|
| `METRICS_ENABLED` | 是否启用指标暴露；`true` 时启动独立 metrics 服务器 | `false` |
| `METRICS_HOST` | metrics 服务器绑定地址，空值监听所有网卡 | (空) |
| `METRICS_PORT` | metrics 服务器端口 | `9090` |

### `METRICS_ENABLED`

**作用：** 开关整个指标功能。关闭时 bilirec 不会监听 metrics 端口，也不会注册任何指标 series，不会增加可察觉的运行开销。

**默认值：** `false`（关闭）。

**何时开启：** 当你部署了 VictoriaMetrics / Prometheus 等监控系统并希望采集 bilirec 数据时。

**注意：** 切换此开关需要重启 bilirec（环境变量配置）。关闭期间累积的计数器值不可观测，重新开启后从 0 重新开始计数。

### `METRICS_HOST`

**作用：** metrics 服务器绑定的网卡地址。空字符串表示监听所有网卡，便于从另一台机器（如树莓派上的 VictoriaMetrics）跨机抓取。

**默认值：** (空字符串，监听所有网卡)。

**何时修改：** 仅本机抓取时可设为 `127.0.0.1` 以减少暴露面；跨机抓取保持空值即可。

### `METRICS_PORT`

**作用：** metrics 服务器监听端口，与主 API 端口（`PORT`）相互独立。

**默认值：** `9090`。

**何时修改：** 当 9090 已被其他服务占用时。

## 指标清单

指标分两类：**资源用量**（进程级，无 label）与**房间级**（带 `room_id` label）。

### 资源用量

| 指标 | 类型 | 说明 |
|------|------|------|
| `go_goroutines` | gauge | Goroutine 数量 |
| `go_memstats_heap_inuse_bytes` | gauge | 堆内存使用量 |
| `go_memstats_stack_inuse_bytes` | gauge | 栈内存使用量 |
| `go_memstats_sys_bytes` | gauge | Go runtime 已向 OS 申请的内存 |
| `process_resident_memory_bytes` | gauge | 进程驻留内存（RSS）。Linux 上包含文件页缓存，录制时会虚高 |
| `process_resident_memory_anon_bytes` | gauge | 匿名页（堆、栈等），不含文件页缓存；更接近程序本身占用（仅 Linux） |
| `process_resident_memory_file_bytes` | gauge | 映射到文件的页（含录制文件页缓存）；这一部分会把 RSS 抬高（仅 Linux） |
| `process_cpu_seconds_total` | counter | 进程 CPU 累计秒数（用 `rate()` 得 CPU 核数） |
| `process_num_threads` | gauge | 进程线程数 |
| `process_open_fds` | gauge | 打开的文件描述符数（仅 Linux） |
| `bilirec_build_info` | gauge=1 | 构建信息，label `version`；仅 release 构建有值 |
| `bilirec_active_recordings` | gauge | 当前正在录制的房间数 |

<Aside type="note">
Go 运行时与进程资源指标由 [VictoriaMetrics/metrics](https://github.com/VictoriaMetrics/metrics) 在抓取时写出（挂在同一套 `/metrics` 上，与房间级指标一起返回）。**没有后台 goroutine** 持续采样。Anon / File 只在 Linux 出现。房间级指标仍由 bilirec 自己注册。
</Aside>

### 房间级指标

所有房间级指标都带 `room_id` label（房间号永不变更，不会因主播改名产生 series 抖动）。

| 指标 | 类型 | 说明 |
|------|------|------|
| `bilirec_room_stream_bytes_total` | counter | 串流写入字节数（≈ 落盘量）。停录后仍留在 `/metrics`，同房间下场继续累加 |
| `bilirec_room_recording_sessions_total` | counter | 录制场次数。停录后仍留在 `/metrics`，同房间下场继续累加 |
| `bilirec_room_recording_active` | gauge 1/0 | 是否正在录制（积分得每日录制时长）。恢复中仍为 1。停录后会从 `/metrics` 消失，历史仍在时序数据库 |
| `bilirec_room_stream_connection_active` | gauge 1/0 | 是否正在从直播流读数据。场次还在、流却断了时为 0。停录后同样会从 `/metrics` 消失 |
| `bilirec_room_stream_connect_attempts_total` | counter | 每次真正去连流算 1 次（含恢复），不是每条备用网址各算 1 次 |
| `bilirec_room_recording_rotations_total` | counter | 切档次数（画质变化切档、恢复后开的新档）。使用者开录的第一档不算 |
| `bilirec_room_recording_start_failures_total` | counter | 开录失败次数（手动与自动开录共用）。label `reason` 见下表。已经在录、正在恢复、正在启动中、使用者取消，都不会加 |
| `bilirec_room_stream_recovery_total` | counter | 断线恢复失败次数（不含正常下播后的重试） |
| `bilirec_room_stream_recovery_success_total` | counter | 断线后再次连上流成功的次数 |
| `bilirec_room_recording_gave_up_total` | counter | 恢复失败后放弃这场录制的次数。label `reason` 见下表。录到设定时长结束、使用者手动停止，都不会加 |
| `bilirec_room_recording_segments_discarded_total` | counter | 这一段没有留下可看的文件。label `reason`：`tiny`（小于 1KB 已删除）、`skipped_small`（过小而未落盘）、`stat_error`（收尾时读不到文件状态） |
| `bilirec_room_recording_pipeline_errors_total` | counter | 写入管线中断。label `reason`：`not_flv`（收到的不是 FLV）、`open`（输出文件打不开）、`other`（含写入失败等） |
| `bilirec_room_live_status` | gauge 1/0 | 是否正在开播（积分得每日开播时长） |
| `bilirec_room_live_sessions_total` | counter | 开播场次数 |
| `bilirec_room_info` | gauge=1 | 房间元信息，label `room_id`、`uname`，用于 Grafana join 显示主播名 |

<Aside type="note">
`bilirec_room_info` 是「info metric」：值恒为 1，作用是把 `room_id` 映射到 `uname`（主播名）。Grafana 查询时用 `* on(room_id) group_left(uname)` join 回数据 series，即可在图例显示主播名。主播改名时只重建这一条小 series，数据 series 不受影响；历史区间会 join 出当时的名字，符合当时的状态。
</Aside>

<Aside type="note">
写入量、场次数、失败次数这类 **counter** 在停录后仍留在 `/metrics`。同一个房间下次开录会接着往上加，这样 Grafana 里的 `increase()` 才能把一段时间内的多场加总。进程重启后这些计数会从 0 再开始；时序数据库里的历史还在，`increase()` 会把重启前后的增量加在一起。

`recording_active`、`stream_connection_active` 这类 **状态 gauge** 停录后会从 `/metrics` 消失，用来看「现在谁在录」。算时长请用时序数据库里的历史，见下表 `integrate()`。
</Aside>

开录失败 `reason` 只会是下面这些固定值，不会把错误全文写进标签：

| `reason` | 常见含义 |
|----------|----------|
| `not_live` | 房间当前未在直播 |
| `empty_urls` | 接口没有返回可用的流地址 |
| `unreachable` | 有流地址，但全部连不上 |
| `disk` | 磁盘剩余空间低于设定下限 |
| `concurrent` | 已达到最大同时录制数 |
| `banned` | 房间被封禁 |
| `encrypted` | 房间已加密 / 付费 |
| `api` | 查询房间或流地址的接口失败（超时、限流等） |
| `other` | 其他开录失败 |

放弃录制 `reason`：`max_attempts`（恢复次数用尽）、`not_live_timeout`（下播后重试超过最长分钟数）、`concurrent`、`banned`、`encrypted`。

场次还在、流却没连上，可以用：

```text
bilirec_room_recording_active == 1 unless on(room_id) (bilirec_room_stream_connection_active == 1)
```

### 弹幕指标

开启房间的弹幕录制后，还会产生带 `room_id` 标签的弹幕相关指标。消息数量指标另外带有 `event_type` 标签，值为 `danmaku`、`super_chat`、`gift` 或 `guard`。

| 指标 | 类型 | 说明 |
|------|------|------|
| `bilirec_danmaku_recording_active` | gauge 1/0 | 当前房间是否正在录制弹幕。停录后同样会从 `/metrics` 消失 |
| `bilirec_danmaku_sessions_total` | counter | 弹幕录制会话次数。停录后仍留在 `/metrics`，同房间下场继续累加 |
| `bilirec_danmaku_connection_active` | gauge 1/0 | 弹幕连接是否在线。停录后同样会从 `/metrics` 消失 |
| `bilirec_danmaku_connection_attempts_total` | counter | 弹幕连接尝试次数 |
| `bilirec_danmaku_reconnects_total` | counter | 弹幕连接重连次数 |
| `bilirec_danmaku_messages_total` | counter | 收到的弹幕、醒目留言、礼物和舰长事件数量 |
| `bilirec_danmaku_messages_dropped_total` | counter | 因写入队列已满而丢弃的事件数量 |
| `bilirec_danmaku_parse_errors_total` | counter | 普通弹幕解析失败次数 |
| `bilirec_danmaku_bytes_total` | counter | 已交给弹幕文件写入器的字节数 |
| `bilirec_danmaku_rotations_total` | counter | 成功切换弹幕文件的次数 |
| `bilirec_danmaku_rotation_dropped_total` | counter | 因切换队列已满而丢弃切换通知的次数 |

<Aside type="note">
弹幕 **counter** 在该房间第一次开始录弹幕时创建，停录后仍留在 `/metrics`。状态 gauge（`danmaku_recording_active`、`danmaku_connection_active`）只在会话进行时出现。`messages_dropped_total` 大于 0 通常表示消息高峰超过了写入速度，可以结合 [弹幕录制](/zh-cn/configuration/danmaku/) 检查 `DANMAKU_OVERFLOW_POLICY`、储存设备和并发录制数。
</Aside>

## Grafana / MetricsQL 查询示例

bilirec 只暴露**累积 counter** 与**即时 gauge**，每日 / 总量统计全部在查询端完成，bilirec 不做任何聚合。

下面表格方便你自己做图或核对算法。已经接好 Grafana 时，也可以把 [Grafana 仪表盘](/zh-cn/configuration/grafana-dashboards/) 当作现成起点。

| 需求 | 查询（MetricsQL） |
|------|------------------|
| 每房间每日写入量 | `sum by (room_id) (increase(bilirec_room_stream_bytes_total[1d]))` |
| 所有房间总量 | `sum(increase(bilirec_room_stream_bytes_total[$__range]))` |
| 当前同时录制 | `sum(bilirec_active_recordings) or vector(0)` |
| 整段平均同时录制 | `avg_over_time((sum(bilirec_room_recording_active) or vector(0))[$__range:5m])` |
| 每天平均同时录制 | `avg_over_time((sum(bilirec_room_recording_active) or vector(0))[1d:5m])` |
| 每天最高同时录制 | `max_over_time((sum(bilirec_room_recording_active) or vector(0))[1d:5m])` |
| 每房间每日录制时长 | `integrate(bilirec_room_recording_active[1d])` |
| 每房间每日开播时长 | `integrate(bilirec_room_live_status[1d])` |
| 每房间每日开播场次 | `increase(bilirec_room_live_sessions_total[1d])` |
| 每房间录制场次 | `increase(bilirec_room_recording_sessions_total[$__range])` |
| 每房间断线恢复失败次数 | `increase(bilirec_room_stream_recovery_total[$__range])` |
| 每房间断线后恢复成功 | `increase(bilirec_room_stream_recovery_success_total[$__range])` |
| 每房间开录失败 | `sum by (reason) (increase(bilirec_room_recording_start_failures_total[$__range]))` |
| 录制中但流没连上 | `bilirec_room_recording_active == 1 unless on(room_id) (bilirec_room_stream_connection_active == 1)` |
| 每房间丢弃的弹幕事件 | `sum by (room_id) (increase(bilirec_danmaku_messages_dropped_total[$__range]))` |
| 每房间弹幕重连次数 | `increase(bilirec_danmaku_reconnects_total[$__range])` |
| 当前 CPU 核数占用 | `rate(process_cpu_seconds_total[5m])` |
| 显示主播名（join） | `... * on(room_id) group_left(uname) bilirec_room_info`，图例用 `{{uname}} ({{room_id}})` |

<Aside type="caution">
**同时录制不要按房间先平均再相加。** 停录后该房间的 `bilirec_room_recording_active` 会从 `/metrics` 拿掉（历史仍在时序数据库）。`avg_over_time` 只会平均「这条序列还在」的时段，而那些时段几乎都是 1；再 `sum` 就会变成「这段时间录过几个房间」，而不是平均同时几路。你可能会看到 7 天平均是 12，但实际同时从未超过 5。

不要写成：

```text
sum(avg_over_time(bilirec_room_recording_active[$__range]))
```

建议算法：先在每个时间点把正在录的房间数加总（没人在录当作 0），再对这些点数取平均或最高。上表「整段 / 每天平均同时录制」「每天最高同时录制」就是这种写法；`[$__range:5m]` / `[1d:5m]` 表示每隔 5 分钟数一次当时在录几路。弹幕的 `bilirec_danmaku_recording_active` 同样。
</Aside>

<Aside type="tip">
**开/下播时刻：** 用 Grafana **state timeline** 面板直接画 `bilirec_room_live_status` 的 0↔1 转换，即可看到每次开播 / 下播的时间点，历史全部保存在 VictoriaMetrics，重启 bilirec 也不丢失。
</Aside>

## 重启与持久化

bilirec **不在本地保存任何指标数据**，所有历史由 VictoriaMetrics 负责：

- counter 只在单次进程生命周期内单调递增。停录不会清零，同一个房间下场会接着加；**重启会归零**，这是设计使然。若某段历史是在停录就拿掉 counter 的旧版本里抓的，那一段的场次 `increase()` 可能仍然偏小；升级后新录制的场次才会按场累加。
- VictoriaMetrics 每次抓取的样本全部入库，`increase()` / `rate()` 会自动识别 counter 重置（值变小视为重启），跨重启的每日统计由重启前增量与重启后增量相加得出。
- 唯一损失窗口：最后一次抓取到重启之间尚未被抓走的增量。以 `scrape_interval=15–30s`、6 Mbps 串流估算，约为 25 MB 量级的误差。
- gauge（`live_status`、`recording_active`、`stream_connection_active`）每轮 / 每事件无条件 Set，重启后自动恢复当前值，不依赖历史。

## 已知限制

- **开播检测精度：** 开启了**开播通知**或**自动录制**的订阅房间，开播状态的更新间隔约为一个订阅检查周期（默认 60–300 秒）。只订阅、未开启这两项的房间，开播状态更新会慢一些，短暂的直播可能不会出现在指标里。
- **追踪范围：** 所有**已订阅**房间都会产生开播状态相关指标（`live_status`、`live_sessions_total`、`room_info`）。未订阅的房间没有这些指标。录制相关 **counter** 只在实际开录后出现，停录后仍留在 `/metrics`；`recording_active` 等状态 gauge 停录后会从 `/metrics` 消失。算同时路数请用上面的「先加总、再对时间平均 / 取最高」，不要 `sum(avg_over_time(...))`。
- **积分边界误差：** `integrate()` 积分法在每场录制 / 开播的首尾有 ≤ 约 2 倍 `scrape_interval` 的边界误差，15–30s 抓取下对小时级录制通常影响不大。
- **`process_open_fds` 平台差异：** 通常仅 Linux 有；Windows 会暴露句柄数，但没有 Anon / File。
- **RSS 含文件页缓存：** `process_resident_memory_bytes` 在 Linux 上包含文件页（`process_resident_memory_file_bytes`，含 Inactive File），监控数字会高于程序本身。看实际占用请对照 `process_resident_memory_anon_bytes`。这两项同样仅 Linux 有。

遇到指标端口连不上、看不到房间指标、Grafana 数据断续等问题，见 [常见问题 · 监控与指标](/zh-cn/guides/faq/#监控与指标)。
